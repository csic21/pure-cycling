# RideEngine 与 GPS 处理

这一份文档解释记录管线里的每一个决定。它是这个项目里最值得仔细读的部分 ——
码表和导航可以慢慢改，但一条错的轨迹已经让骑手损失了打开这个 App 的理由。

---

## 管线

```text
BLE 传感器 SensorReading ────────────────────┐
                                             │ onSensorReading()
原始定位 LocationFix                         │ 心率 / 踏频 / 功率 / 轮速
   ↓  校验            GpsFilter              │
   │                                        │ 时间戳倒退 / 精度太差 /
   │                                        │ 速度不可能 / 重复
   ↓  平滑            GpsFilter              │ EMA + 死区，非对称平滑
   ↓  距离            DistanceCalculator     │ 锚点 + 半径门限
   ↓  爬升            ElevationAccumulator   │ 阈值参考点
   ↓  统计            RideEngine ←───────────┘
   ↓  持久化          RideRecorder  批量写入 + 检查点
```

顺序是固定的。先校验再平滑，因为未经校验的采样会悄悄把一个坏点洗成「看起来正常」的值。

传感器读数由 `SensorManager` 归一化后，经 `RideRecorder` 进入引擎：订阅在骑行开始时建立、
在拆解引擎时取消，读数落在 `RideState.sensors` 和此后每个轨迹点上。

这里曾经断过一次，值得记下来：manager 能配对、能在自己的页面显示实时值，
但**没有任何东西订阅 `readings`**，引擎永远收不到心率，而引擎自己的测试全绿 ——
因为它测的是 `onSensorReading`，不是「有没有人调它」。
现在 `ride_recorder_test.dart` 里有一条从读数到落盘轨迹点的端到端测试锁着。

## 1. 校验：什么样的定位不该被信任

规格 §13 列出了四条规则，实现如下：

| 条件 | 处理 |
|---|---|
| `accuracy > 50m`（可配置） | 不计入里程，**但界面仍显示精度** |
| 瞬时速度 > 100 km/h | 判定为异常 |
| 1 秒内跳跃 500m | 丢弃 |
| 时间戳倒退 | 丢弃 |

### 精度差和信号丢失是两件事

这是 UI 上最重要的一条区分：

- **精度差**（`gpsPoor`）：定位在来，但不可用。距离被扣住不累加。
- **信号丢失**（`gpsSignalLost`）：超过 15 秒没有定位。

骑手在高架桥下需要知道这两者的区别：前者说明「有信号但不好」，后者说明「彻底没了」。
两种情况的应对完全不同（继续等 vs. 换位置）。

### 隧道之后的重新捕获

长时间没有定位后重新捕获时，引擎不会无条件接上那条线段：

```dart
if (dtSeconds > longGapSeconds && impliedSpeed > longGapMaxSpeedMps) {
  // 120 秒的间隔里平均速度超过 20 m/s —— 骑手很可能在这段时间里拐了弯。
  // 直接连起来是编造一个不存在的直线段。
  重新锚定，不计距离;
}
```

反过来说，如果间隔很长但平均速度合理（骑手确实一直在骑），就正常累加 —— 那 3 公里的隧道
被正确连接起来，而不是凭空消失。

## 2. 平滑：速度为什么不能只信 GPS

规格 §12 明确说「不要完全信任 GPS 返回的 speed」。实现里结合了三个来源：

```dart
_smoothSpeed(
  reported: 设备报告的 Doppler 速度,
  derived:  distance / dt 计算出来的速度,
  distanceMeters: 本段距离,
  dtSeconds: 时间差,
  accuracy: 水平精度,
)
```

### 融合规则

| 情况 | 处理 |
|---|---|
| 两者都有且接近 | 加权平均，偏向设备报告值（Doppler 更平滑）。多普勒可信时权重 0.8 |
| 多普勒更高，且速度精度够紧或水平精度 ≤ 25 m | 采信多普勒。位置算出来的速度会晚一两个点 |
| 多普勒更低 | 采信多普勒，这是在刹车 |
| 多普勒不可信且更高 | 取较小的那个 |
| 只有一个可用 | 用它 |
| 多普勒停在 0，人还在规划路线上 | 用沿路线进度算出来的速度（不低于 1.5 m/s，4 秒内）。已有 ≥ 0.5 m/s 的多普勒、轮速、确认停下，都不让它覆盖 |
| 都不可用 | 没有运动传感器时，保持上一个值并轻微衰减，读起来像「滑行」而不是跳变。加速度计确认还在动时，上一笔多普勒速度最多再显示 25 秒；确认停住、且定位已安静 3 秒，立刻归零。振动不能恢复一次已经自动暂停的骑行 |

「派生速度不可用」的判断是 `距离 < 3m` 或 `dt < 0.5s`。短到那个程度的线段上，
除法会把噪声放大成任意大的数字。

### 平滑：可信的多普勒马上跟上，刹车仍然马上落下

默认上升权重是 0.25，从 0 爬到巡航要好几秒。多普勒已经被判定可信、而且读数在上升时，
权重改成 0.85，一个点就能进码表。下降仍用两倍权重、上限 0.7：自行车可以急刹车，
停下之后不能再把巡航速度留在自动暂停的判定里。

### 完全静止时直接判定

```dart
if (distanceMeters < 2.0 && reportedUsable && reported < 2.0) {
  _smoothedSpeed = reported;   // 不做平滑，直接采信
  return;
}
```

位置完全没动、设备也报告几乎没动的时候，没有任何歧义需要平滑掉。

没有这条规则，指数衰减需要好几秒才能从巡航速度落到静止，而那几秒里自动暂停还没开始计时 ——
一个配置为 5 秒的自动暂停，骑手实际要等约 10 秒。这是测试发现的。

### 精度影响平滑权重

多普勒还没被判定可信时：精度 > 20m 权重乘以 0.6（更依赖历史值），精度 < 6m 乘以 1.4
（更相信新采样）。可信多普勒的上升不走这条，直接用 0.85。

## 3. 距离：为什么门限是半径

**这是整个项目里最值得读的一段。**

### 直觉上正确的做法是错的

「忽略与前一点距离小于 N 米的采样」，然后累加剩下的 —— 这个设计看起来很合理，但它是错的。

静止的 GPS 接收机不是收敛在一个点上，而是**来回摆动**：解算结果在几米范围内游走，
连续两个采样相距 10 米是完全正常的。任何小到能保住真实骑行的逐点阈值
（比如 3 米）都会让这种摆动畅通无阻 —— 而且因为摆动是正负交替的，
它会**全部累加起来**。停 60 秒可以凭空多出 600 米。

### 正确的做法：围绕锚点的半径

```dart
if (meters < radiusFor(accuracyMeters)) {
  return 0;      // 不计距离，而且不移动锚点
}
```

采样在半径内时，**锚点保持不动**。围绕一个固定点的摆动永远逃不出半径范围，
无论摆动幅度多大、持续多久。

半径随精度缩放：

```dart
radius = clamp(accuracy × 2, 12m, 25m)
```

精度差的定位不只是「不够准」，而是**不够确定**，诚实的回应是要求更多证据才相信它。

### 关键性质：延迟，不是丢弃

采样最终越过半径时，**从锚点起的完整距离一次性入账**。

所以一个真的移动了 15 米的骑手会拿到他的 15 米 —— 只是要等到第三秒。
唯一损失的是骑行结束在半径中间时的那最后几米，而这低于任何消费级 GPS 的分辨率。

对 20 km/h 的骑行，这意味着每 3 秒入账约 16.7 米，总计准确到 1% 以内。

### 第二道门：慢速漂移

```dart
if (impliedSpeed < minSpeedForDistanceMps) {   // 0.7 m/s ≈ 2.5 km/h
  return 0;      // 也不移动锚点
}
```

接收机在两分钟里漂移 40 米（0.33 m/s）时，速度门会拦住它 —— 半径门单独拦不住，
因为 40 米显然超出了 12–25 米的半径。

而骑手如果真的在缓慢爬坡，锚点会一直被保持，等速度上来时那段距离仍然入账。

### 第三道门：不可能的速度

```dart
if (impliedSpeed > maxSpeedMps) {   // 30 m/s ≈ 108 km/h
  _anchor = point;    // 重新锚定到新位置
  return 0;
}
```

关键是**重新锚定**而不是单纯丢弃：骑行要从骑手实际所在的地方继续，
而不是拖着一个越来越远的陈旧参考点。

## 4. 爬升：为什么不累加每个正增量

把 GPS 海拔曲线里每个上升的差值都加起来会得到荒谬的数字 ——
一次平坦的骑行可以「爬升」400 米，因为消费级 GPS 高度计的 ±2 米漂移
和一个真实的短坡在幅度上完全一样。

### 阈值参考点

```dart
final delta = altitude - _reference;
if (delta >= thresholdMeters) {        // 2 米
  _gain += delta;
  _reference = altitude;
} else if (delta <= -thresholdMeters) {
  _loss += -delta;
  _reference = altitude;
}
```

参考点只在曲线**真正离开它超过阈值**时才移动。小幅振荡被吸收，永不计数；
持续爬坡在突破阈值时完整计入。

代价是刻意接受的：非常短的爬坡会被牺牲，换来总量的诚实。
骑手会比较不同骑行之间的总爬升，一个每次都上下浮动几百米的数字，
比一个漏掉了 5 米小坡的数字更糟。

### 海拔本身先经过死区

```dart
if (delta.abs() < altitudeDeadbandMeters) return previous;   // 0.3 米
_smoothedAltitude = previous + alpha * (raw - previous);     // alpha = 0.12
```

死区保证静止时高度条不会抖动；EMA 让真实的高度变化平滑地跟随。

## 5. 自动暂停

两个阈值，各自带独立的停留时间：

```text
speed < 2 km/h 持续 5 秒  → 暂停
speed > 3 km/h 持续 2 秒  → 恢复
```

单阈值会抖动：速度正好在 2 km/h 时会一秒钟暂停恢复好几次，
产生跳动的读数、碎片化的移动时间，更糟的是让 GPS 过滤器不得不反复重新锚定。

### 移动时间 vs 骑行时间

| 字段 | 累计时机 |
|---|---|
| 骑行时间（elapsed） | status 是 riding 时（**包含**自动暂停） |
| 移动时间（moving） | status 是 riding 且**未**自动暂停时 |

平均速度的分母是**移动时间**。否则每个红绿灯都会拉低这个数字。

默认码表同时显示两者，正是为了让这个区别可见。

### 用户暂停会抑制自动暂停

手动暂停后，自动暂停控制器被静默，直到用户主动恢复 —— 两者不能互相争夺状态。

### 加速度计可以让暂停来得更早，仅此而已

手机有加速度计时，它确认「车确实停着」可以把上面那个 5 秒缩短到 **2 秒**：
低速段的速度是接收机最不可靠的输出，而「完全没在抖」是强得多的证据。
省下的那几秒本来会被记进移动时间，也就是平均速度的分母。

反方向被**刻意封死**：传感器说「在动」时，规则一个字都不改。

- 它不能让暂停提前（口袋里的振动不算骑车）；
- 它不能让一次暂停提前结束（恢复照旧看速度）；
- 它不能让一次骑行一直停在 `riding`。一辆停在路边、旁边有怠速发动机的车
  如果能把整段骑行钉在 `riding`，移动时间会虚高 —— 那是平均速度的分母。

没有传感器、或者读数断了 3 秒以上时是 `null`，三个判断全部退回只看速度。
理由、阈值来源和真机验证清单在 [phone-sensors.md](phone-sensors.md)。

## 6. 状态机

```text
idle ──start()──→ preparing ──beginRecording()──→ riding ⇄ paused
                     │                              │
                     │ 20 秒超时                     │ stop()
                     └──────────────┐               ▼
                                    └──→ riding   finishing → finished
```

`preparing` 状态存在的理由是规格 §4 的倒计时。它也顺便解决了另一个问题：
第一个定位通常很粗糙，会在大约三十秒里逐渐变好，倒计时正好覆盖这段窗口。

**20 秒超时后无论如何都会开始记录。** 规格 §4 说得很明确：信号弱要警告，但不能阻止开始。
骑手在地下车库按了开始，App 不能什么都不做。

## 7. Crash Recovery

检查点每 5 秒写一次，包含：

```text
ride_id, status, started_at
elapsed, moving, distance, max_speed
elevation_gain, elevation_loss
last_lat/lng/altitude, last_sequence
smoothed_speed, smoothed_altitude
anchor_lat/lng, anchor_timestamp       ← 距离计算器的锚点
```

锚点是必需的：没有它，恢复后的第一段会从「原点」算起，
把检查点位置和恢复位置之间的位移编造成距离。

### 顺序保证

```dart
void _onCheckpoint(RideCheckpoint checkpoint) {
  unawaited(() async {
    await _flushPoints();                    // 先落盘轨迹点
    await _activeRideDao.save(checkpoint);   // 再写检查点
  }());
}
```

检查点记录的 `lastSequence` 如果对应的点还没落盘，恢复时就会跳过它。

### 恢复时以数据库为准

```dart
final storedMax = await _maxStoredSequence(checkpoint.rideId);
final resumeFrom = storedMax > checkpoint.lastSequence
    ? storedMax
    : checkpoint.lastSequence;
```

检查点可能落后数据库一次 flush，所以取两者较大值。

## 8. 测试

`app/test/ride_engine_test.dart` 用 `fake_async` 同时控制**假时钟**和**假定时器队列**。

同时控制两者是关键。引擎从墙上时钟读取定位时间戳，而 ticker、自动暂停和信号丢失判定
都由真实的 `Timer` 驱动。只推进假时钟而不推进定时器队列，测试会安静地通过 ——
而引擎实际上一次都没 tick 过。这正是会发布出去的那类 bug。

```dart
void withRide(void Function(void Function(Duration) advance, DateTime Function() clock) body) {
  fakeAsync((async) {
    var now = DateTime.utc(2026, 9, 23, 6);
    body(
      (d) { now = now.add(d); async.elapse(d); },   // 两者一起推进
      () => now,
    );
  });
}
```

测试覆盖：

- 生命周期：preparing → riding、弱信号不阻塞开始、暂停冻结移动时间但不冻结骑行时间
- 距离：稳定骑行、完全静止无距离、传送门定位被拒
- 自动暂停：延迟后暂停、超阈值后恢复、单次慢速采样不触发、可关闭
- 爬升：有坡时有爬升、平地噪声不产生爬升
- 传感器：心率/踏频/功率进入状态和轨迹点、不可能的值被丢弃 —— 引擎层；
  从管理器的读数到落盘轨迹点的接线由 `ride_recorder_test.dart` 覆盖
- 崩溃恢复：检查点按节奏写入、恢复不产生幽灵线段、序号从检查点继续
- GPS 状态：精度差 vs 信号丢失的区分

## 9. 可调参数

全部在设置界面里，全部有合理默认值：

| 参数 | 默认 | 位置 |
|---|---|---|
| 自动暂停速度阈值 | 2 km/h | 设置 → 骑行 |
| 自动暂停延迟 | 5 秒 | 设置 → 骑行 |
| 恢复速度阈值 | 3 km/h | 设置 → 骑行 |
| 恢复延迟 | 2 秒 | 设置 → 骑行 |
| 有效精度上限 | 50 米 | 设置 → 骑行 → GPS |
| 信号丢失判定 | 15 秒 | 设置 → 骑行 → GPS |
| 定位精度档位 | 高精度 | 设置 → 骑行 → GPS |
| 检查点间隔 | 5 秒 | 编译期（`RideEngineConfig`） |
| 距离半径下限 | 12 米 | 编译期（`DistanceCalculator`） |
| 爬升阈值 | 2 米 | 编译期（`ElevationAccumulator`） |
